Getting Started and Technician Safety

1. Confirm authorization, scope, asset identity and the user's actual symptom. Record reproducible steps, onset, recent changes and business impact. Avoid passwords, recovery secrets and unrelated personal information.

2. Verify toolkit media and target disk separately. COC USB #1 is the Lexar USB Flash Drive, serial CONFIGURE_USB_SERIAL, MBR, 61,865,984,000 bytes, exFAT data volume COC_USB_1. Drive letters and disk numbers can change between computers and recovery environments. Never identify a target by letter alone.

3. Record device model, Windows version/build/architecture, firmware mode, storage layout, encryption status and backup state. Use a known-good power source. Check remaining space on both the toolkit and backup destination.

4. If a disk clicks, disappears, reports critical errors or produces repeated I/O failures, stop repair and repeated scans. Prioritize a controlled image to separate media or escalate to professional recovery. Healthy-looking SMART does not certify a disk.

5. Collect narrowly relevant evidence before changing anything. Choose one justified change at a time, record output and retest the original symptom. Obtain separate approval for destructive recovery, account resets and security-sensitive changes.

6. Never format, repartition, initialize, wipe, bypass credentials, disable security controls or clear target logs as part of this toolkit update. Preserve Ventoy, the seven ISOs, driver backups and rollback copies.

Environment prerequisites

Windows PowerShell 5.1 is the baseline for the new extensions; the preexisting menu may prefer PowerShell 7 when available. Organizational execution policy may prohibit scripts. Use an approved signing or policy process; the new extension launchers do not override execution policy. Run diagnostic checks as a standard user first. Some storage, event, Defender, BitLocker and repair operations require an elevated terminal. A failed or unavailable check is not a clean bill of health.

The Windows menu and scripts require installed Windows. WinRE/WinPE may lack PowerShell, Storage modules, network drivers and vendor GUI dependencies. Follow the text recovery procedure when scripting support is absent. Use x64 tools on compatible x64 Windows; ARM64 and x86 builds are retained for appropriate systems and are not redundant deletion candidates.

Hardware Diagnostics

For no power, inspect the adapter, cable, socket, charging indicators and physical damage. Follow the manufacturer's supported power-reset procedure. Do not open swollen batteries or continue charging a visibly damaged unit; route to qualified hardware service. For no display, distinguish lack of POST from a display/output problem using indicator codes and a known-good monitor. Record OEM diagnostics results.

For overheating or shutdowns, compare temperature behavior under the actual workload using HWiNFO. Inspect airflow and fan behavior. Avoid stress tests on unstable hardware. For battery complaints, run the existing battery diagnostic launcher, compare design capacity with full charge capacity and examine discharge history. A battery report is evidence, not a definitive replacement decision.

For intermittent memory errors, document symptoms and use Memtest86+ from Ventoy on a compatible machine. Record pass count, errors and module configuration. Test reproducibility and reseat/replace only through authorized hardware work. Memory information from Windows is not a memory test.

For storage complaints, inspect CrystalDiskInfo or smartctl attributes and device errors. Interpret manufacturer-specific SMART values carefully. Do not run CHKDSK repair or write-heavy tests on a failing drive. For USB problems, compare a known-good port/cable/device using USB Device Tree Viewer; USBDeview supplies historical device information. Device removal actions are separate changes.

Windows Repair

Does Windows boot?

If it boots, capture the error and recent update/driver history. Review relevant events, reliability information and free space. The original guided technician script and automated session are useful screening tools. Use the repair extension only after identifying an actual servicing/system-file problem. The extension's default invocation previews a command; -Apply still requires elevation, USB verification and typed target confirmation.

Online command choices are DISM CheckHealth, ScanHealth and RestoreHealth, then SFC verify-only or repair as indicated by results. RestoreHealth can use Windows Update. Preserve CBS and DISM output; compare before/after behavior. These utilities do not fix all driver, hardware, account or application failures. A reboot and symptom-specific validation remain necessary. Microsoft: repair a Windows image.

If Windows does not boot

1. Establish whether firmware detects the intended disk. Compare firmware boot mode with the installation layout. Preserve current firmware settings; do not disable Secure Boot by default.

2. Boot the Windows recovery ISO or trusted WinRE environment through Ventoy. Select repair options rather than installation. Try appropriate built-in Startup Repair or known restore options only after backup and target confirmation.

3. Use diskpart inspection only: list disk, list volume, then exit. Determine the physical disk, Windows directory and system partition. Windows might not be C: in recovery. The USB itself must never become a boot repair target.

4. Run manage-bde -status. If locked, follow authorized key recovery. Do not repair an inaccessible installation.

5. Preserve data to separate storage. If disk failure is suspected, stop servicing and prioritize imaging or specialist recovery.

6. Use the preserved Original Offline Windows Repair Playbook, reproduced in this master reference, for offline SFC/DISM and escalation. A Windows folder alone does not prove the target. Select a compatible source image/index for the actual Windows edition, architecture, language and servicing state.

Boot configuration repair is a deliberate manual operation

BCDBoot rebuilds boot files from a selected Windows installation. The source Windows directory, destination system partition and UEFI/BIOS mode must be positively identified first. Example placeholders are not ready-to-run commands: bcdboot W:\Windows /s S: /f UEFI. When /s is used, BCDBoot does not create the normal UEFI NVRAM entry; that distinction matters when validating boot recovery. Back up relevant boot configuration first and preserve multi-boot requirements. Do not format the system partition or automatically run bootrec, bcdboot or bootsect. Microsoft BCDBoot reference.

Success requires cold boot and restart from the intended internal disk with the USB removed, appropriate recovery-environment availability, and no unexpected encryption prompt. If evidence is ambiguous, escalate rather than guessing partition identities.

Account and Encryption Recovery

Distinguish a Microsoft account, local account, Active Directory account, Entra account and Windows Hello PIN. Check keyboard layout, Caps Lock, connectivity, date/time and the exact error. Use the account owner's official recovery process or an authorized enterprise administrator. A PIN problem is not necessarily a password problem. Avoid repeated attempts that trigger lockout.

For local accounts, use the owner's configured recovery options or an already-authorized administrator. Before a password reset, consider consequences for EFS-encrypted files, saved credentials and protected application data. Domain lockout investigations should identify the affected account, timing and known services/devices under the organization's procedure. Do not collect passwords into reports, edit offline SAM files, use password-removal utilities or replace accessibility binaries.

For BitLocker, record the recovery key ID and asset context, never the 48-digit secret in ordinary reports. The owner may have the key in their Microsoft account, their organization's account/directory, a printout or another approved backup. Match the key ID and let the authorized owner/admin enter it. If no key is available, recovery cannot legitimately decrypt the data; stop and escalate. Do not automatically decrypt, suspend protection, change TPM settings or remove protectors. Microsoft BitLocker key recovery.

After legitimate recovery, investigate the triggering firmware, hardware or boot change, verify protection state and use approved enterprise key handling. Any reimaging decision needs separate approval and a documented data-loss decision.

Authorized encrypted-volume unlock without recording the secret

Match the recovery key ID shown by the recovery prompt or the metadata-only BitLocker diagnostic with the owner/admin recovery record. In installed Windows, the authorized owner can open Explorer, select the locked volume, choose Unlock, then the recovery-key option, and enter the verified key directly into the Windows UI. In a Windows recovery startup prompt, the owner enters it there. The technician does not capture the secret in reports, clipboard notes, command examples or USB files. Verify access to the intended volume and protection/lock status afterward; do not decrypt, suspend protection or change TPM/boot settings as a default action. If the UI or authorized key is unavailable, stop and escalate rather than bypass encryption.

Account-specific recovery routing

Local account: use the owner's configured reset/security-question options or an already-authorized administrator, considering EFS and protected-data consequences before a reset. Microsoft account: the owner uses Microsoft's official recovery route and enters secrets themselves. Active Directory: an authorized delegated administrator investigates lockout cause and resets/unlocks only the selected account under organizational policy. Entra: use the owner's configured self-service recovery or the authorized tenant administrator; verify intended tenant and authentication method. Windows Hello PIN issues need the supported owner PIN-recovery path and are not automatically password failures. Record authorization/result, never passwords.

Networking

Work from physical/link state to addressing, routing, DNS, transport and the application. Compare one affected device with a known-good device on the same network. Preserve configuration before changing anything. Do not use a network reset as the first response.

1. Link: inspect adapter status, Wi-Fi signal and cable/port behavior. The Wi-Fi script provides local diagnostics; do not export stored wireless passwords.

2. Addressing: check address, mask, gateway, DHCP lease and unexpected self-assigned address. The DHCP script gathers evidence; avoid release/renew on critical remote sessions without a recovery path.

3. Gateway and route: examine routes and test the relevant gateway. An ICMP failure alone does not prove an endpoint is down.

4. DNS: compare resolution through the configured DNS server, suffix/search behavior and the actual destination. On a domain member, check organizational DNS rather than substituting a public resolver.

5. Transport/application: test the authorized destination and port. Validate proxy, VPN, firewall scope and TLS/application errors separately. Inspect firewall profiles without disabling the firewall.

6. Throughput: iperf3 requires an authorized server peer. Distinguish local link capacity from internet performance. Nmap and Angry IP Scanner require a written permitted target range; do not scan arbitrary enterprise networks.

7. Packet capture: Wireshark needs a functioning capture driver for live capture. The USB holds the Npcap installer, not proof of an installed driver on each PC. Installation is a separately approved host change; verify licensing and current compatibility first. Opening saved captures can work without live capture access.

PuTTY and WinSCP support authorized administration and transfers. Verify host keys and avoid saving passwords on the shared USB. Review portable WinSCP configuration for sensitive session information before lending the toolkit. Java remains pending approved dependency cleanup. Angry IP Scanner is broken and excluded from operational menu additions.

Security and Malware Triage

Confirm the reported indicators and follow the organization's incident-response instructions. Preserve time, evidence and relevant events before remediation. Coordinate isolation when warranted; disconnecting a remote managed endpoint can prevent collection and support. Do not automatically disable Defender, firewall, encryption, Secure Boot or enterprise controls.

The security collector records Defender status, firewall profiles, BitLocker status, Secure Boot, TPM and hotfix inventory. No recovery protectors or secrets are requested. These checks do not constitute a vulnerability scan, forensic acquisition or certification of security. Hotfix inventory is not complete patch-compliance evidence. Use authorized enterprise tools for compliance and detection history.

Inspect startup and process evidence with the existing Sysinternals suite. Understand the impact before terminating processes or deleting persistence. Antivirus remediation, quarantine removal and offline scanning can change evidence and need a deliberate plan. No offline antivirus definitions are assumed bundled. For suspected compromise, preserve original evidence and consider verified clean reinstallation under the organization's incident process instead of declaring a scan result sufficient.

Restrict access to captures, dumps, reports and driver inventories. They can contain names, network addresses, paths or device identifiers. Do not email or publish them without explicit authorization. Store recovery keys separately in approved secure systems. Ordinary file deletion is cleanup, not guaranteed secure erasure of flash storage.

Deployment and Migration

Pre-change checklist

Document target hardware, firmware mode, disk identities, Windows edition/build/architecture, activation/licensing, app inventory, encryption, enrollment, important data and OEM drivers. Verify backups by restoring a sample. Ensure suitable AC power, network access if needed, storage capacity and a rollback path. The toolkit USB is not the sole backup destination.

File migration

Use the COC-Migration script for ordinary selected files to a new directory on a separate backup disk. Default mode runs robocopy's listing preview. -Copy requires a typed confirmation and does not merge an existing destination. It excludes destructive mirror/move behavior and rejects cloud placeholders, reparse points and EFS-encrypted entries for manual resolution. This wrapper preserves data/attributes/timestamps but does not migrate apps, credentials, profile settings or security ACLs. Robocopy codes 8 and above indicate failure; lower codes still require reviewing output and verifying the backup. Microsoft Robocopy reference.

Example syntax, with operator-selected real paths:

powershell.exe -NoProfile -File U:\Scripts\Toolkit\COC-Migration.ps1 -Source "C:\Users\Owner\Documents" -Destination "B:\Backups\Case-001\Documents"

Replace U: with the verified toolkit letter and B: with separate verified backup storage. Add -Copy only after reviewing the preview and confirming access. Hydrate and verify cloud data first. Use the owner's approved EFS certificate/key export process where applicable. Do not copy a live profile wholesale and expect accounts or applications to work on another PC. Verify file counts, sample hashes, application import and user acceptance before retiring the original data.

For state/settings migration at enterprise scale, USMT is a separate Microsoft ADK component using ScanState and LoadState. It needs a tested configuration and supported source/target scenario. It is not present in the audited USB inventory and this release does not claim to install it. Microsoft USMT overview.

Imaging and reinstall

Clonezilla is already available as a boot ISO for deliberate image capture/restore. Save images to separate storage, record exact source/destination devices and use image verification. Restoration overwrites data and requires a separate approved operation; it is not automated here. For fragile disks, SystemRescue and a carefully controlled recovery plan may be more appropriate than routine imaging. Restore-test on spare compatible hardware when feasible.

For Windows reinstall, preserve licenses, drivers, data, recovery keys and enrollment requirements first. Verify official compatible installation media rather than assuming Windows11_Recovery.iso contains a particular edition/build. Windows Setup and disk/partition changes are manual and separately approved. Never alter the Ventoy toolkit's partitions to create deployment media. Post-deployment validation includes drivers, activation, updates, security controls, management enrollment, network access, applications, restored data, reboot and owner acceptance.

USMT profile/state migration

Problem: preserve approved user data/settings during a supported Windows client migration.

Scope: staged amd64 USMT 10.0.26100.9457, extracted from Microsoft-signed downloaded ADK MSI/cabinets. Requires elevation and a separately protected migration store. USMT is not a general disk clone or application installer. It does not support Windows Server, Entra-joined or hybrid-Entra scenarios, and does not migrate Store app settings. Destination applications should be installed before restoration. Check current supported source/destination versions, architecture and user mapping. Microsoft requirements, migration scope.

Prerequisites: authorization for the selected user, independent backup, known source/target versions, reviewed MigXML, adequate separate-disk capacity, AC power, approved secret management and a disposable restore test.

Safety: never store encryption keys or plaintext credentials on the toolkit. Do not use /o to overwrite an existing store or /c to silently continue with ignored errors. Do not capture all users by default. Review cloud placeholders, EFS and application data. Use an approved encrypted backup destination or independently protected USMT store and key handling. Encryption is not automatically enabled by the examples below; do not run them against personal data until the store is appropriately protected.

Tools: USMT folder, MigDocs.xml/MigApp.xml and vendor help. Start an elevated PowerShell terminal: right-click Start, select Terminal (Admin), and accept only the authorized elevation prompt. Discover the toolkit letter in Explorer first. Set these variables to actual verified locations and the authorized account:

$toolkit = 'U:\'
$usmt = Join-Path $toolkit 'Tools\Windows\USMT\amd64'
$store = 'B:\ProtectedMigration\Case-001'
$account = 'SOURCEPC\Owner'

Procedure: run vendor help first from a case working folder on protected storage. ScanState and LoadState are administrator tools. In this environment even /? returned code 34, insufficient rights, so actual capture/restore acceptance is blocked pending an elevated test system. Microsoft return codes.

& (Join-Path $usmt 'scanstate.exe') /?
& (Join-Path $usmt 'loadstate.exe') /?

Estimate selected-user scope with reviewed rules before capture. /ue:* excludes unselected users; /ui selects the explicitly authorized account. Choose log paths on protected case storage, not an ordinary shared toolkit report area when user data may be sensitive:

& (Join-Path $usmt 'scanstate.exe') $store "/i:$usmt\MigDocs.xml" "/i:$usmt\MigApp.xml" '/ue:*' "/ui:$account" '/p:B:\ProtectedMigration\estimate.xml' '/l:B:\ProtectedMigration\estimate.log' '/v:5'

For a new, protected store after reviewing the estimate, the corresponding ScanState command omits /p. Preserve logs, return code and rule files. Validate the store with USMTUtils and inspect vendor guidance for the particular format/encryption options; do not guess key parameters. Perform LoadState only on the positively identified destination with applications preinstalled and an explicit tested user mapping. LoadState restores state and changes the target; it has no general no-change preview:

& (Join-Path $usmt 'loadstate.exe') $store "/i:$usmt\MigDocs.xml" "/i:$usmt\MigApp.xml" '/l:B:\ProtectedMigration\restore.log' '/v:5'

Expected results: only selected planned user data/settings, no skipped critical files, comprehensible logs, correct target identity. Troubleshooting: stop on unsupported join/build scenarios, code 34, incompatible rules or missing files. Verification: test restore on a disposable supported client, sign in as the mapped user, compare critical file counts/hashes and app settings, and obtain owner acceptance before retiring the source. Escalation: EFS, unsupported Entra state, lost store keys, inconsistent mappings or unsupported build. Related procedures: ordinary file migration, profiles, deployment handover.

DISM image servicing and offline drivers

Problem: inspect or service a deliberately selected offline Windows image.

Scope: existing DISM in supported Windows/WinPE. Prerequisites: compatible image, architecture/build/edition/language, verified separate working disk, documented target, backup, elevation and approved change. Safety: no formatting, partition creation, applying images or boot modifications during ordinary diagnostics. Work on a copy of the image. Never assume W: or the image index below is correct.

Tools/procedure: use image metadata to select the correct index; list drivers from an identified offline Windows volume. These commands inspect without applying an image:

dism.exe /Get-WimInfo /WimFile:"B:\Images\approved.wim"
dism.exe /Image:W:\ /Get-Drivers /Format:Table

Mounting modifies a selected working folder and requires a planned lifecycle. Create a new empty folder on separate working storage and mount read-only for inspection:

dism.exe /Mount-Image /ImageFile:"B:\Images\approved.wim" /Index:1 /MountDir:"B:\ImageWork\Mount" /ReadOnly
dism.exe /Unmount-Image /MountDir:"B:\ImageWork\Mount" /Discard

Offline driver addition is a modification, requires approved vendor-signed compatible INF packages and a recoverable image. On an identified offline installation, the documented operation is dism /Image:<verified-root> /Add-Driver /Driver:<approved-INF-directory> /Recurse. Do not use /ForceUnsigned or copy random drivers. Image application can overwrite data; it is a separately approved deployment step performed from appropriate recovery infrastructure, not a menu test.

Expected results: correct image metadata/driver inventory, successful unmount and no unintended target changes. Troubleshooting: record native code and DISM log; stop if mount state is unclear or architecture/source differs. Verification: verify mount cleanup, boot and driver/device behavior after an actual approved servicing operation. Escalation: encrypted/inaccessible image, unsupported servicing or uncertain target. Related: offline repair, drivers, Clonezilla rollback. Microsoft DISM driver servicing.

Repeatable application deployment: WinGet, MSI and EXE

Problem: repeat approved app installation reliably. Scope: an explicitly authorized target and official/licensed package. Prerequisites: backup/rollback, correct architecture, installation context, source signature/hash verification, dependency checks and licensing authorization. Safety: do not execute untrusted packages, silently accept contracts, reuse unsigned MSI modifications or assume an EXE's switches. Each target install is a change; never run it merely to test the toolkit.

Tools/procedure: WinGet requires its installed client, supported target and appropriate source/network access. Inspect exact package identity and version first:

winget.exe --version
winget.exe show --id APPROVED.PACKAGE --exact

After explicit target approval, use the documented install command pinned to the approved version and scope. Do not add agreement-acceptance flags unless that acceptance is authorized. Offline deployment uses verified local installers; WinGet is not assumed offline or present in WinPE.

Capture the failing workload, timing, resource pressure and recent changes. Use Process Explorer for process/resource inspection, Autoruns for startup investigation and PerfView/WPA for appropriate traces. Process Monitor: narrow an application/file/registry failure

Problem: reproduce a specific application access or startup failure. Scope: authorized Windows target and a bounded workload. Prerequisites: backup/evidence policy, storage budget, permission for the tool's required driver/elevation, and the relevant application/process name. Safety: captures can contain confidential paths and activity; do not collect unrelated users or use destructive remediation during capture.

Tools: the existing Sysinternals Process Monitor (Procmon64.exe on a suitable x64 Windows target). Open it from the Sysinternals folder and handle its license/elevation prompts yourself. Step-by-step: stop capture with Ctrl+E, clear only the tool's current disposable capture view with Ctrl+X when appropriate (this does not clear Windows logs), open Filter with Ctrl+L, set an Include filter for the intended process and relevant path/operation, start capture, reproduce the symptom once, and stop promptly. Preserve the original captured evidence before narrowing views further. Do not clear a needed captured trace or delete the underlying log as a diagnostic shortcut.

Expected results: events correlated with the failure time/process. Interpret ACCESS DENIED, NAME NOT FOUND and sharing violations in context; normal programs also produce failed probes. Troubleshooting: elevation/driver restrictions, overly narrow filters or missing workload reproduction can hide evidence. Verification: after an approved targeted fix, capture the same bounded reproduction and compare the outcome. Escalation: sensitive investigation, kernel/tool incompatibility or uncertain impact. Related: application crashes, NTFS permissions, incident retention and baseline/handover.

Save an explicitly authorized case trace to separate protected storage, or the designated held temporary session as Procmon.pml within the stated size/privacy budget. No capture is created automatically by the toolkit.

Process Explorer and Autoruns: inspect before changing

Problem: high resource use, startup delay or suspected persistence. Scope: the affected endpoint and relevant workload. Prerequisites: timing, original symptom, authorization, stable power and an evidence/rollback plan. Safety: process termination and startup disabling are changes that can affect security and data; they are not part of ordinary inspection.

Tools: existing Process Explorer and Autoruns in the Sysinternals folder. Step-by-step: in Process Explorer, sort the relevant resource column and inspect the actual process tree/properties to correlate CPU, memory and handles with the workload. In Autoruns, inspect the relevant startup tabs and path/publisher entries; record a baseline before a separately approved change. Do not apply blanket disabling, delete persistence or assume unsigned means malicious. Operator handles EULA/elevation requirements; the toolkit does not auto-accept.

Expected results: scoped process/startup evidence that explains the symptom or identifies a lead. Troubleshooting: protected processes, missing privileges and unsupported driver versions may limit visibility. Verification: repeat the workload/startup after one approved change and compare resource/time behavior. Escalation: potential compromise, critical services or changes without a safe rollback. Related: malware triage, configuration baseline and handover.

WinDbg: analyze an authorized crash dump

Problem: repeated Windows/application crashes. Scope: approved dump evidence and an appropriate matching debugger. Prerequisites: stop code/time, Windows/build/architecture, permitted symbol source/cache, controlled dump storage and authorization to inspect sensitive memory. Safety: do not copy dumps or expose memory excerpts by default; a stack/module name is not automatically the cause.

Tools: existing WinDbg. Step-by-step: open the authorized dump through File > Open Crash Dump, select the approved symbol configuration/cache through the debugger's symbol settings or vendor help, and inspect analysis output. In the debugger command pane, !analyze -v requests detailed crash analysis. Preserve the native analysis and compare recurring patterns with drivers, events and hardware evidence. Symbol downloads require an appropriate network connection; use a validated cache offline.

Expected results: usable symbols and a contextual analysis rather than unresolved stacks. Troubleshooting: missing symbols, wrong architecture, truncated dumps and unavailable source data limit conclusions. Verification: confirm a proposed cause through independent evidence and retest after an approved fix; compare any subsequent dump. Escalation: specialist debugging, sensitive data, kernel corruption or uncertain diagnosis. Related: blue-screen workflow, driver compatibility and evidence preservation.

PerfView: collect or analyze a bounded trace

Problem: workload-specific performance failure. Scope: the affected process/workload and a short approved collection interval. Prerequisites: current functioning PerfView, required privileges, a known reproduction, space/privacy budget and vendor help. Safety: ETW traces can capture sensitive activity; avoid uncontrolled capture length or stress on unstable hardware.

Tools: existing PerfView, which the user reports launching successfully. Step-by-step: use the Collect menu and its collection dialog to select only relevant options and an approved output destination, start collection, reproduce the workload once, stop, then open the resulting trace and examine the relevant CPU/event/GC views. For an existing trace, open it directly and correlate time/process context. Respect the application's documented compressed/rundown output formats; use protected case storage when output is not one of the designated cleanup-manager filenames. No script starts a trace automatically.

Expected results: a bounded trace with the relevant workload represented. Troubleshooting: privilege/provider support, symbol/network dependency, collection settings and sparse samples affect interpretation. Verification: compare equivalent before/after workloads following one approved fix. Escalation: unsupported recording environment, sensitive incident evidence or analysis beyond your scope. Related: slow-computer workflow, temporary-output retention and handover.

Controlled hardware health and burn-in

Problem: intermittent instability that basic screening does not explain. Scope: an authorized spare/affected device with a suitable OEM/vendor test procedure. Prerequisites: verified data backup, stable AC power, healthy-looking storage, known hardware limits and permission for a controlled workload. Safety: stop immediately for thermal shutdown, abnormal noises, storage failures, burning smell, swelling or visible damage. Do not invent a universal safe temperature or run stress tests on failing media.

Tools: existing HWiNFO only under applicable licensing, CPU-Z for inventory, Memtest86+ for an appropriate memory test, SMART tools and the device manufacturer's approved diagnostics. Step-by-step: collect idle measurements, choose one relevant vendor-supported workload, observe thermals/power/error behavior, stop at the defined limit/error, and record exact settings, elapsed duration and pass/error details. Memtest86+ runs from appropriate boot media; Secure Boot may block its unsigned binary, so use an approved compatible environment rather than silently disabling security.

Expected results: reproducible workload observations and explicit tests, not a certification from the read-only health screen. Troubleshooting: firmware compatibility, drivers/sensors, ambient conditions and test limitations matter. Verification: repeat only when new evidence or a change warrants it; retest the original symptom. Escalation: failing storage, persistent memory errors, cooling/power faults or hardware work outside authorization. Related: no-power/no-display, overheating, storage and crash workflows. Reports and Cleanup

New extension diagnostics, repairs and migrations write only to Reports\COC-Managed\COC-<timestamp>-<unique-id>. Each completed session records filenames, lengths and SHA256 hashes in .coc-session.json. This provenance record is an operational safeguard, not a cryptographically signed chain of custody. Anyone who can edit the USB can tamper with its files; keep trusted release baselines separately.

The cleanup menu starts with a full preview, then allows numbered individual file selection and shows exact deletion paths. It requires a typed count-specific confirmation and repeats identity/path/hash checks. Changed files, unlisted filenames, invalid manifests, junctions and paths outside the managed report area are excluded. It never recursively deletes directories. Manifests remain as an audit record.

Old Reports content is intentionally untracked and ineligible for automatic cleanup. Folder names alone do not prove ownership. Review existing files and explicit exact deletion targets separately before any approved legacy cleanup. Driver backups, personal backups, original logs, tools and rollback copies are excluded. Never clear Windows Event Logs, CBS, DISM, security events or target PC diagnostic history through toolkit housekeeping.

Cleanup supports individual file numbers, CATEGORY=Network/Hardware/Diagnostics/Repair/Migration, SESSION=exact-session-name, or ALL. It shows count/path/bytes, requires typed confirmation and repeats ownership/path/hash/identity checks. Known legacy reports are eligible only through the audited exact-path/hash ownership registry; later untracked output stays excluded. Create Reports/COC-Retention-Holds/legacy.hold to hold all registered legacy reports. Locked/changed items remain; partial failures return code 2 and report actual deleted bytes.

Designated temporary output: COC-Cases -Action NewTemp creates an active managed session with a retention hold. Save only specifically authorized tool output using the exact names PerfView.etl, Procmon.pml, CrashDump.dmp or temporary.txt. Use CompleteTemp with the exact session name to preview files and record hashes after typed ownership confirmation. Release the hold only after retention/investigation review; CATEGORY=Temporary can then select eligible output. Limit a temporary session to 4 GB; use separate protected evidence storage for larger/sensitive acquisitions. Target-machine logs remain untouched.

Session metadata is shown as a separate eligible target only when all files in that completed, unheld session are eligible and there are no untracked files/subfolders. It cannot be deleted before its payload files. Selecting the full session/all list deletes eligible payload first and metadata last after the same exact-count confirmation; locked or failed payload keeps metadata protected. Empty session folders remain. Both logical deleted bytes and observed free-space change are reported.

Event exports default to time/ID/provider/severity metadata. Use the filtered event script's -IncludeMessages only for a clear diagnostic need and -SecurityAuthorized for authorized Security-log access. Pattern redaction removes known credential labels and 48-digit recovery-password patterns, but cannot detect every secret; review sensitive exports before sharing. No target event log is cleared.

Reference and Escalation

Before install: verify USB identity, baseline v8 hash and backup, free space, source package hashes, destination collisions and no unexpected reparse points. Keep the installation journal and original menu outside the active path. Do not overwrite unknown files.

After install: verify every deployed file hash, navigation labels, referenced paths, document links, search and script syntax. Test new menu choices without running a repair on a healthy laptop. Use synthetic report fixtures to validate cleanup preview, refusal paths, selective deletion and unrelated-file preservation. Run migration tests only with disposable known input on separate test media; compare copied hashes and restore behavior. Exercise repair failure/permission/cancellation paths before an approved actual repair.

Physical acceptance: boot all seven ISOs in supported firmware modes on spare hardware; test device access, suitable memory test duration, sample imaging/restore, actual recovery and representative migration. Capture the exact machine, mode, tool version, result and limitations. Never label static checks as boot tests or production readiness.

Rollback: restore the installation's original menu or the independently verified v8 backup after verifying its expected hash. Leave original tools/docs untouched. If removal of extension files is desired, show exact extension paths and obtain separate deletion approval. Preserve newly generated reports until the operator chooses their retention. File rollback does not undo any target PC repair or migration; those actions have their own recovery plan.

# COC Ultimate IT Technician Toolkit
## Offline Windows Repair Playbook v1.0

Purpose: Diagnose and repair authorized Windows installations that cannot boot normally.

SAFETY RULES
- Confirm authorization before accessing or repairing a computer.
- Identify the physical disk and Windows installation before any repair.
- Never assume Windows is installed on C: inside WinRE or WinPE.
- Never assume Disk 0 is the intended repair target.
- Preserve irreplaceable data before changing partitions, boot files, or system files.
- Never format, initialize, clean, or repartition a disk during initial diagnosis.
- Do not bypass BitLocker. Obtain the legitimate recovery key.
- Do not run boot-changing commands automatically.
- Record all changes and results.

## 1. Start With Diagnosis

1. Document the reported problem and recent hardware/software changes.
2. Check hardware health, particularly storage and RAM.
3. If the drive appears physically unreliable, prioritize recovery or imaging.
4. Boot Windows Recovery Environment or an appropriate trusted recovery environment.
5. Determine whether the failure involves Windows, storage, encryption, or boot configuration.

## 2. Identify the Windows Installation

From Windows recovery Command Prompt:

    diskpart
    list disk
    list volume
    exit

These commands are for inspection only.

Check candidate drive letters individually:

    dir W:\Windows
    dir W:\Windows\System32

Replace W: with the actual candidate drive letter.

Verify the physical disk, volume size, filesystem, and installation path.

A Windows folder alone is not sufficient proof that a volume is the correct repair target.

Do not run repairs until the target is positively identified.

## 3. Check BitLocker

From an elevated recovery Command Prompt:

    manage-bde -status

If the target volume is locked, obtain its legitimate recovery key through the authorized recovery process.

Do not attempt repairs against an inaccessible encrypted installation.

Never store recovery passwords in unencrypted technician reports.

## 4. Protect User Data

Before modifying the installation:

- Ask whether important files have been backed up.
- Evaluate disk health.
- If storage failure is suspected, stop repair attempts and prioritize imaging/recovery.
- Confirm the backup destination is a different physical storage device.
- Verify recovered files or backups before proceeding.

Avoid unnecessary writes to failing drives.

## 5. Windows Startup Repair

First consider the built-in Startup Repair feature in Windows Recovery Environment.

If Startup Repair fails:

- Review the error or log.
- Confirm the Windows installation and boot mode.
- Inspect the EFI System Partition and boot configuration.
- Do not blindly execute commands copied from generic internet guides.

## 6. Offline System File Checker

After identifying the correct offline Windows directory and boot directory, the general syntax is:

    sfc /scannow /offbootdir=<BOOT_ROOT> /offwindir=<WINDOWS_DIRECTORY>

Example placeholders must be replaced with verified paths.

The boot root and Windows directory are not necessarily on the same volume.

Do not run against the technician's currently running Windows installation by mistake.

## 7. Offline DISM

Offline Windows image servicing uses a target such as:

    dism /Image:<OFFLINE_WINDOWS_VOLUME_ROOT> /Cleanup-Image /ScanHealth

Repair operations may require a compatible Windows image source.

Verify Windows version, architecture, and servicing compatibility before using a repair source.

Do not run RestoreHealth automatically or assume internet access is available.

## 8. UEFI Boot Recovery

UEFI systems normally use an EFI System Partition containing boot files.

BCDBoot can recreate Windows boot files, but using the wrong source or destination can alter the wrong installation.

General syntax:

    bcdboot <WINDOWS_DIRECTORY> /s <VERIFIED_EFI_VOLUME> /f UEFI

This is a REPAIR command, not a diagnostic command.

Never run it until:
- The Windows installation has been verified.
- The EFI partition has been verified.
- The target computer's boot mode has been confirmed.
- User data and recovery requirements have been considered.
- The technician explicitly approves the change.

Do not use BootSect or BootRec blindly on modern UEFI installations.

## 9. Registry and Event Log Investigation

Offline registry hives and Windows event logs can provide useful diagnostic evidence.

Prefer read-only inspection or working copies.

Do not load, edit, or replace offline registry hives without an explicit recovery plan and backup.

## 10. Repair Completion

After a repair:

1. Confirm Windows boots normally.
2. Verify user files remain accessible.
3. Check storage and filesystem health.
4. Check device drivers and networking.
5. Review relevant Windows errors.
6. Record commands executed, outcomes, and outstanding issues.
7. Confirm the computer can restart successfully.

## 11. When to Stop

Stop and reassess if:

- The physical drive is failing.
- The correct target disk cannot be identified.
- BitLocker recovery information is unavailable.
- Data preservation has not been addressed.
- A repair could overwrite important boot or recovery information.
- The required Windows image source is unverified or incompatible.

A successful repair must not come at the expense of recoverable user data.
